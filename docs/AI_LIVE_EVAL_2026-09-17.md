## Observations
1. Most accurate: gpt-4o — best category agreement (52/65 of successful outputs, 52/73 overall), fewest rejections (8), zero invariant violations and zero wrong deductions; but it approved none of the 16 cases labeled ok+deductible (its one raw approval, bank-fee, was lost to item 8). gpt-4o-mini: 49/64, 1/16 approved, 1 violation per run. gpt-4.1-mini: 46/59, 3/16 approved, 14 rejections, one wrong deduction (item 4). Status agreement is 42–45/73 for every model, so no model is production-ready on the current prompt.
2. Over-asking dominates. Of the 16 cases with a saved business purpose and an entity on file (labeled ok+deductible), runs 1/2/3/4 approved 1/0/3/1; the rest came back needs_more_info (14/16/10/14) or were rejected outputs (1/0/3/1). The first question is usually "Is this used exclusively for business, or is there any personal use?" (7 of 16 over-ask cases in each gpt-4o-mini run) although the saved purpose already answers it; gpt-4.1-mini instead demands receipts (`missing_fields: documentation_status`, 4/12) despite the prompt's "a missing uploaded receipt is a recordkeeping reminder". Tuning input: say explicitly that a recorded purpose with no personal-use indication supports an `ok` business suggestion.
3. Over-approving (ok on a needs_more_info/blocked label): 1/3/1/0 cases per run, all `ok` + `is_deductible=false` personal classifications (costco-mixed-flag and gym-membership-over-eager by gpt-4o; blocked-by-model by all) — no deduction slipped through that path.
4. **P0** — a wrong deduction the grounding cannot see: gpt-4.1-mini (run 3, `irs-estimated-tax`, IRS USATAXPYMT $1,500, note "Q2 estimated federal tax payment") returned `status=ok, transaction_kind=expense, is_deductible=true, expense_type=business, category=other, deductible_percent=100, confidence=0.95`, reasoning "Estimated tax payments are ordinary and necessary expenses for a self-employed individual to cover income tax liabilities", evidence `business-162, records-334`. `groundTransactionAnalysis` accepted it (category `other` + `business-162` is "applicable"; no gate covers tax payments), and the scorecard counted it as a status and category match — it is visible only in `ok_with_deduction=4`. Federal income-tax payments are never a Schedule C expense; add a grounding gate for government/tax-payment merchants and treat `is_deductible=true` on category `other` as review-required.
5. Invariant violations (gpt-4o-mini, 1 per run, different cases): `adobe-no-purpose` (run 1) and `studio-rent-separate-location` (run 4): "unresolved result claims an unconditional deduction". Raw run-4 output shows the phrase "…to determine if it is fully deductible" in `reasoning_summary` of a model-issued needs_more_info; the sanitizer at `lib/ai/transaction-tax-policy.ts:280` only inspects `customized_reason`, so `reasoning_summary`/`key_analysis_factor`/`audit_risk_rationale` reach the UI unfiltered (run-1 raw JSON was not captured; same class). P1.
6. Claims policy (words maximize / guaranteed / fully deductible / file your taxes / audit protection): "fully deductible" appears in displayed `customized_reason` of 4 gpt-4o-mini cases per run (run 1: client-lunch-attendees, studio-rent-separate-location, verizon-null-percent-provided, upwork-contractor; run 4: client-lunch-attendees, verizon-with-percentage, airbnb-conference, prior-personal-once), always as "To determine if it's fully deductible…" — the contraction "it's" bypasses the `(is|are) fully deductible` regex. Zero hits for the other four terms in any run; zero displayed hits for gpt-4o and gpt-4.1-mini (one gpt-4.1-mini raw hit was sanitized).
7. Provider failures are all `AI_INVALID_OUTPUT` (no rate limits, refusals or 5xx). Causes from raw JSON: (a) evidence-id choice not in the grounding's category→evidence table — e.g. `home-587` for apartment rent under `rent`, `business-162` only for `equipment`, `records-334` for nondeductible expenses (IRS payment, personal Uber, bank fee), `business-162/personal-262` for meals/travel — 8/9 gpt-4o-mini, 5/8 gpt-4o, 6/14 gpt-4.1-mini; (b) `status=ok` with `is_deductible=null` (gpt-4.1-mini 6/14, gpt-4o 1/8); (c) `evidence_ids=null` for unknown-kind movements (venmo-no-note, zero-amount); (d) 4 evidence ids where the zod schema allows 3 but the JSON schema has no `maxItems` (gpt-4.1-mini 2/14). Most of these are honest needs_more_info answers lost to citation strictness — a 11–19% failure rate per pass.
8. Percent-scale ambiguity: neither the prompt nor the JSON schema states that `deductible_percent` is 0–100. gpt-4o answered on a 0–1 scale (`0.4` for the three Verizon 40% cases, `1` for bank-fee) and gpt-4o-mini once (`1`, venmo-contractor-payment run 4); the grounding reads `1` as 1% and its `deductible_percent < 100` mixed-use gate turned both correct approvals into needs_more_info. gpt-4.1-mini used `100`. Fix: state the scale in the prompt (or reject/normalize fractional values) — this alone removes gpt-4o's only lost approval.
9. Category disagreements are frequently defensible: `equipment` for a laptop/desk/gear labeled supplies/home_office/other, `meals_50` for shoot-day snacks, `travel` vs `vehicle_expense` for rideshares, `other` for unidentified Amazon items; the label itself encodes over-eager synthetic outputs in several cases (see notes). Grounding-driven mismatches (`personal-credit-with-note`, `amazon-refund-credit`) are not model errors.
10. Corpus hygiene: three case pairs send byte-identical prompts (listed above) and two `rejected` labels cannot be matched live; the `ok_with_deduction` count is the only scorecard field that exposes wrong approvals — add an explicit "wrong deduction" metric (ok+deductible on a nondeductible label). The `gpt-5.x` family is one parameter rename away from being testable (`max_tokens` → `max_completion_tokens`); all `*-chat-latest` aliases are dead.
